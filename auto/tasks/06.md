# 06 — Profile the demos with NVIDIA tools and capture explainable metrics

## Goal
Run the key Hybrid API and LLM demos under NVIDIA profiling tools so the study can show concrete GPU/runtime evidence instead of only application-level timings.

## Required profiling coverage

Use the tools that are actually installed and supported on the pinned machine/TornadoVM SHA, prioritising:

- `nvidia-smi` for device identity, utilization, memory use, clocks, and process-exclusivity checks;
- Nsight Systems (`nsys`) for CPU/GPU timelines, CUDA API calls, kernel launches, synchronization, transfer behavior, stream usage, and host launch overhead;
- Nsight Compute (`ncu`) where available for kernel-level metrics such as achieved occupancy, memory throughput, instruction mix, SM utilization, tensor-core activity when relevant, and stall reasons;
- `ptxas -v`, `cuobjdump`, `nvdisasm`, or equivalent current-toolchain inspection when generated CUDA code/PTX/SASS evidence materially explains a result.

## Method

- Keep **timed** runs separate from **profiled** runs.
- Record the full command line for every profiler invocation.
- Capture profiler versions and the exact TornadoVM SHA.
- Use deterministic inputs and a controlled GPU state.
- Save raw reports under `results/profiling/` or tool-specific subdirectories.
- Extract concise machine-readable summaries for the talk under `results/metrics/`.
- Never quote a profiler-collected wall-clock number as the primary benchmark timing unless the task explicitly explains why the profiling overhead is irrelevant.
- Prefer profiler views that answer a presenter question: Where did the time go? How many launches? How much host overhead? Are kernels memory- or compute-bound? Are transfers avoidable?

## Talk outputs

Produce a short evidence table for each flagship demo:

- metric;
- observed value;
- exact profiler/source of the value;
- run id;
- interpretation;
- caveat.

Also generate a presenter-friendly checklist of the 3–5 most useful metrics to display live or show in a slide.

## Run conventions

Where the demo has a Java arg-file, include the canonical `java @arg-file ...` command in the profiler recipe. Include a tested JBang variant when practical, or document why profiling requires a fuller TornadoVM launch environment.

## Acceptance

- At least one flagship Hybrid API demo has a successful `nsys` profile or a captured blocker.
- At least one compute-heavy demo has an `ncu` profile or a captured blocker.
- Raw reports and extracted metrics are committed/recorded appropriately.
- `docs/claims.md` cites the profiler artifacts for every profiler-derived claim.
- `docs/demo-runbook.md` contains the exact profiling commands and explains which metrics are worth showing to an audience.
